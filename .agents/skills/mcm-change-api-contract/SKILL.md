# MCM API 계약 변경

API 계약을 단일 기준에서 시작해 모든 의존 산출물에 순서대로 반영한다.

## 1. 변경 여부 판별

다음 중 하나라도 바뀌면 계약 변경으로 취급한다.

- 경로, HTTP 메서드, 인증 또는 권한
- 요청 헤더, 파라미터, 본문 필드
- 응답 필드, 상태 코드, 오류 코드·형식
- 리소스 상태 전이 또는 열거값
- DB 테이블, 컬럼, enum, 제약, 인덱스, RLS 정책
- Mock 예시나 클라이언트 타입이 표현하는 공개 동작

내부 구현만 바뀌고 외부 관찰 가능한 동작이 동일한 경우에는 계약 변경이 아닌 근거를 남긴다.

## 2. 기준과 승인 확인

먼저 `AGENTS.md`, `AI_RULES.md`, `docs/PROJECT_CONTEXT.md`, `docs/COLLABORATION.md`, `docs/API_CONTRACT.md`와 관련 계약 파일을 읽는다. `mcm-reborn/` 구현에 영향이 있으면 `mcm-reborn/AGENTS.md`와 `mcm-reborn/package.json`도 읽는다. `openapi.yaml`을 HTTP API의 기계 판독 가능한 최종 기준으로 삼는다.

편집 전에 다음을 확인한다.

- 계약 변경 전용 이슈와 변경 이유가 있다.
- 영향받는 화면, 서버, 데이터, 기존 호출자를 식별했다.
- 호환성, 마이그레이션, 롤백 방안을 설명할 수 있다.
- 프론트엔드와 백엔드 담당자의 승인이 있다.

필수 승인이나 제품 결정이 없으면 제안과 영향 분석까지만 작성하고 계약 및 구현 파일을 수정하지 않는다. 2주 MVP와 이후 로드맵의 경계가 달라지는 경우에도 먼저 사용자 승인을 받는다.

## 3. 계약 우선 순서로 변경

다음 순서를 유지한다.

1. `openapi.yaml`의 스키마와 성공·오류 예시를 갱신한다.
2. `mock-data.json`과 공유 타입·상수를 동기화한다.
3. `mcm-reborn/app/api/`의 Route Handler 등 서버 구현과 `supabase-schema.sql` 또는 마이그레이션을 반영한다.
4. `mcm-reborn/`의 클라이언트 호출, 공유 타입과 UI 상태 처리를 반영한다.
5. 통합 테스트와 `MCM_REBORN_API_GUIDE.md`, 관련 `docs/` 문서를 갱신한다.

한 단계만 바꾸고 의존 산출물을 오래 불일치 상태로 남기지 않는다. 호환성을 유지할 수 있으면 추가 필드, 기본값 또는 단계적 폐기를 우선한다.

## 4. 보안과 상태 규칙 보존

- 인증 주체와 리소스 소유권 검사를 명시한다.
- 권한 거부와 존재하지 않는 리소스를 구분한다.
- 결제·상태 변경 요청은 중복 호출과 재시도를 고려한다.
- 오류 응답의 구조와 코드 체계를 일관되게 유지한다.
- DB 변경은 제약, 인덱스, RLS, 기존 데이터 변환과 롤백을 함께 검토한다.
- 비밀값이나 실제 고객 데이터를 예시에 넣지 않는다.

## 5. 정합성 검증

- YAML과 JSON을 파싱하고 `$ref` 대상을 확인한다.
- 모든 엔드포인트의 정상·오류·빈 결과·권한 경로를 확인한다.
- OpenAPI 예시와 Mock, 타입, 서버 응답이 같은 필드와 열거값을 사용하게 한다.
- DB 제약과 API 상태 전이가 충돌하지 않는지 확인한다.
- 저장소의 계약 검증, 테스트, 타입 검사, 빌드를 실행한다.

계약 변경에는 `python validate_package.py`를 실행한다. `mcm-reborn/`도 영향받으면 저장소 루트에서 `npm --prefix mcm-reborn run lint`, `npm --prefix mcm-reborn run typecheck`, `npm --prefix mcm-reborn run build`를 실행하며, 의존성 재현이 필요하면 먼저 `npm --prefix mcm-reborn ci`를 실행한다.

현재 자동 테스트 스크립트가 없으므로 테스트 성공을 주장하지 말고 검증 공백으로 기록한다. 실행하지 못한 검사는 이유를 기록한다. 결과 보고에는 변경 전후 계약, 영향 범위, 승인 상태, 마이그레이션·롤백, 실제 검증 결과를 포함한다.

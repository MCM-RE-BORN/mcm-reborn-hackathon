# 협업 규칙

이 문서는 MCM RE:BORN에서 사람과 코딩 에이전트가 함께 작업하는 운영 기준이다. 모든 변경은 작은 이슈, 제한된 범위, 검증 가능한 계약과 사람 리뷰를 전제로 한다.

## 1. AI와 사람이 맡는 결정

| 영역 | AI에 맡길 수 있는 초안·보조 작업 | 사람이 최종 결정할 작업 |
|---|---|---|
| 기획 | 아이디어 확장, 사용자 스토리·위험·발표 구조 초안 | 문제 중요도, 사용자 정의, 기능 우선순위, 과장 여부 |
| 디자인 | UX 문구, 상태·접근성·컴포넌트 변형 정리 | 정보 구조, 사용자 흐름, 시각 위계, 최종 사용성 |
| 프런트엔드 | 컴포넌트·타입·테스트 초안, 반복 코드, 리팩터링 후보 | 상태 구조, API 경계, 패키지, 성능·보안 판단 |
| 백엔드 | CRUD·스키마·테스트·문서·migration 초안 | 권한, 무결성, 트랜잭션, 비밀정보, 외부 실패 정책 |

에이전트 요청에는 한 가지 사용자 결과, 확정된 계약, 수정 가능 파일, 금지사항과 테스트 조건을 함께 적는다. “서비스 전체를 완성”하는 식의 넓은 요청은 이슈로 분리한다.

## 2. 작업 보드와 소유권

작업 상태는 `Backlog → Ready → In Progress → Review → QA → Done` 순서로 이동한다.

- 이슈마다 담당자 한 명과 수정 예정 파일을 지정한다.
- 한 사람은 동시에 하나의 `In Progress` 이슈만 맡는다.
- 하루 안에 끝나지 않을 작업은 독립적으로 검증·병합 가능한 이슈로 나눈다.
- 프런트엔드와 백엔드가 같은 변환 로직이나 계약을 중복 구현하지 않도록 소유권을 정한다.
- 에이전트는 사용자나 이슈가 허용한 범위 밖 파일을 임의로 수정하지 않는다.

## 3. Definition of Ready

다음 조건이 충족되어야 `Ready`에서 구현을 시작한다.

- 담당자와 우선순위가 지정되어 있다.
- 해결할 사용자 문제와 기대 결과가 적혀 있다.
- 정상·오류·빈 상태·권한을 포함한 검증 가능한 완료 조건이 있다.
- 포함 범위, 제외 범위, 의존 작업이 적혀 있다.
- UI 작업에는 화면 설명·디자인, API 작업에는 요청·응답·오류 계약 또는 Mock이 있다.
- 계약이나 제품 결정을 바꾸는 작업에는 필요한 사전 승인이 있다.

핵심 정보가 없어 결과가 달라질 수 있으면 구현을 멈추고 질문한다. 기존 패턴으로 안전하게 정할 수 있는 세부사항은 가정을 명시하고 진행한다.

## 4. 우선순위

| 등급 | 기준 | 대응 |
|---|---|---|
| P0 | 배포 불가, 데이터 손상, 로그인 불가, 핵심 데모 전체 중단 | 다른 작업을 멈추고 즉시 대응 |
| P1 | 핵심 흐름 일부 실패, 주요 환경에서 동작하지 않음 | 당일 수정 |
| P2 | 우회 가능, 일부 화면·메시지 오류 | 기능 동결 뒤 중요 항목만 수정 |
| P3 | 미세한 간격·문구, 비핵심 개선 | 여유가 있을 때 처리 |

기능 동결 이후에는 P0, P1과 중요한 P2만 변경한다. 마지막 단계의 전면 재작성이나 광범위한 리팩터링은 금지한다.

## 5. 브랜치와 커밋

- 최신 `develop`에서 작업 브랜치를 만든다.
- 이름은 소문자와 하이픈을 사용해 `feature-*`, `bugfix-*`, `hotfix-*` 형식으로 짓는다.
- `main`과 `develop`에 직접 push하지 않고 모든 변경은 PR로 병합한다.
- 커밋 유형은 `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore` 중 하나를 사용한다.
- 한 커밋과 PR에는 관련 없는 포맷 정리나 리팩터링을 섞지 않는다.
- 브랜치 생성, 커밋, push, PR 생성은 명시적으로 요청된 범위에서만 에이전트가 수행한다.

## 6. Pull Request

- 한 이슈를 한 PR로 해결하고 대상 브랜치는 원칙적으로 `develop`으로 한다.
- PR 템플릿에 목적, 변경, 제외 범위, 검증 결과, 데모 영향, 롤백 방법을 작성한다.
- 새 패키지가 필요하면 이유, 검토한 대안, 승인자를 기록한다.
- API 계약 변경은 별도 이슈와 프런트엔드·백엔드 양쪽 승인을 연결한다.
- 사용한 AI 도구, 맡긴 범위, 사람이 직접 검토한 항목과 미확인 위험을 공개한다.
- 필수 CI와 사람 리뷰가 끝나기 전 병합하지 않는다.
- 작성자는 자신의 PR을 승인하지 않으며 팀이 정한 병합 권한을 따른다.
- 작성자가 코드 흐름과 주요 판단을 리뷰어에게 설명할 수 없으면 병합하지 않는다.

## 7. 구현 안전 규칙

- 기존 아키텍처, 타입, 컴포넌트와 라이브러리를 우선 재사용한다.
- 실제 저장소의 버전·타입과 공식 문서를 확인하고 존재하지 않는 API를 추측하지 않는다.
- 승인 없이 새 프레임워크·패키지, 계약 변경, 전체 재작성, 테스트 삭제를 하지 않는다.
- API 키, 토큰, 개인정보와 운영 데이터를 코드·프롬프트·로그·Fixture에 넣지 않는다.
- 실패·빈 값·권한·중복 요청·외부 서비스 실패를 성공 경로와 함께 다룬다.
- 사용자의 기존 변경을 보존하며 관련 없는 파일을 되돌리지 않는다.

## 8. Definition of Done

- 구현자가 직접 실행해 완료 기준을 확인했다.
- 정상·오류·빈 상태·권한 경계를 검증했다.
- 관련 테스트를 추가했거나 재현 가능한 테스트 방법을 기록했다.
- 적용 가능한 lint, 타입 검사, 테스트와 빌드가 통과했다.
- 실행하지 못한 검사는 이유와 남은 위험을 기록했다.
- 사람 리뷰와 QA 또는 스테이징 확인을 마쳤다.
- 관련 문서, 계약, Mock과 데모 데이터가 동기화되었다.
- 핵심 데모와 폴백 흐름을 깨뜨리지 않는다.

검증 명령은 저장소 루트 기준으로 다음과 같이 실행한다.

```bash
# 협업 문서·템플릿·스킬
python -X utf8 scripts/validate_collaboration.py

# OpenAPI·Mock·DB·AI 예시 계약
python validate_package.py

# Next.js 앱
npm --prefix mcm-reborn ci
npm --prefix mcm-reborn run lint
npm --prefix mcm-reborn run typecheck
npm --prefix mcm-reborn test
npm --prefix mcm-reborn run build
```

현재 `mcm-reborn/package.json`의 native Node 테스트는 OpenAI 요청·폴백·이미지 범위와 Meshy quota·오류·복구 정책을 검증한다. 외부 LIVE·브라우저·DB 통합 검사는 별도 staging 검증과 수동 확인 결과를 남긴다.

## 9. 운영 리듬과 기록

- 매일 담당 작업, 차단 사항, 당일 통합 대상을 짧게 공유한다.
- 매일 통합해 장기 브랜치와 큰 충돌을 피한다.
- 주 2회 이상 스테이징에서 핵심 데모를 처음부터 끝까지 확인한다.
- 승인된 제품·기술 결정은 `docs/DECISIONS.md`에 남긴다.
- 규칙 충돌이나 예외가 필요하면 영향과 기한을 기록하고 사람의 승인을 받는다.

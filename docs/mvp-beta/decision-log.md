# MVP 베타 결정 로그

이 문서는 MVP 산출물과 저장소 계약·Figma 사이의 충돌을 기록한다. 기존 저장소의 승인 결정은 `docs/DECISIONS.md`가 계속 담당한다.

> D-001~D-012는 **2026-08-17 기준 historical**이다. 삭제하지 않고 당시 판단을 보존하되, 현재 구현·검증에는 [`../MVP_DEMO_CANONICAL.md`](../MVP_DEMO_CANONICAL.md)와 아래 D-013~D-018을 적용한다.

## 2026-08-17 현재 결정

### D-013 — Canonical 우선순위

- **무엇을:** 사용자 최종 원칙과 `docs/MVP_DEMO_CANONICAL.md`를 기존 계약·정적 베타 경계보다 우선한다.
- **왜:** 현재 MVP의 목적은 최종 기획을 자연스럽게 완주하는 서비스 데모이며, 이전 UI/계약 우선 결정이 전문가 검수 시점과 화면 데이터를 왜곡했다.
- **대체:** D-001의 “API·DB 미변경 정적 UI” 경계와 D-010의 혼합 규칙 중 충돌 부분.

### D-014 — 촬영·업로드 규칙

- **무엇을:** 정면·측면·내부·각인 4슬롯, JPG/JPEG·PNG 최소 3장·최대 4장, 장당 10MB를 적용한다. 모바일 실제 카메라와 파일 폴백을 제공한다.
- **왜:** 최종 와이어프레임과 모바일 촬영 시연을 따른다. 시리얼은 별도 선택 입력이다.
- **대체:** D-002와 D-009의 카메라 정적 진입점 결정.

### D-015 — AI 예상치와 정품 카피

- **무엇을:** 중앙 Fixture/seed로 예상 재활용률 72%, 정품 사전 적합도 예상 91%를 제공한다. 91%는 주문 적합 참고 신호이며 정품 확정이 아니다.
- **왜:** 실제 AI가 어려운 판단을 안정적으로 시연하면서 정품·제작 확정 오인을 막는다.
- **대체:** D-003의 이분법적 `NOT_EVALUATED`/수동 검토 중심 프레젠테이션.

### D-016 — 주문 후 실물 검수와 변경 승인

- **무엇을:** Mock 결제로 `ORDER_PLACED`를 만든 뒤 수거·입고·공식 장인 실물 검수를 수행한다. 골든 경로는 `CHANGE_REQUIRED`이며 68%, 195,000원, 4~5주 변경안을 고객이 승인한다.
- **왜:** 전문가 판단은 AI 기반 주문 후 마지막 점검이어야 한다. 고객 승인 전에는 제작하지 않는다.
- **대체:** D-005의 정적 조건 변경 variant, D-011의 결제 직후 승인 대기와 별도 완료 주문 분리.

### D-017 — 단일 중앙 시나리오

- **무엇을:** 원제품 `MCM 비세토스 모노그램 백팩(2019, 5년 이상)`, 희망 제품 `RE:BORN 여권지갑`, 접수 `SUB-RB-20260817-0001`, 주문 `RB-20260817-0001`, 보증서 `ESG-RB-20260817-0001`을 전 화면에서 공유한다.
- **왜:** 기존 와이어프레임과 베타 화면의 제품·날짜·식별자·가격·재활용률 분리를 제거한다.
- **대체:** D-011과 D-012의 프레젠테이션 주문·식별자 분리.

### D-018 — 목업·외부 기능의 데모 구현

- **무엇을:** 실제 AI·3D·결제·물류·검수 외부 연동은 Fixture와 정적 자산으로 시연할 수 있다. 실제 카메라는 구현하되 나머지는 재현 가능한 데모 동작이면 충분하다.
- **왜:** 핵심은 기술 완성보다 서비스 흐름의 자연스러운 완주다.
- **대체:** D-009의 모든 복잡 기능을 비활성 진입점으로만 두는 결정.

## Historical 결정 — 2026-08-13~2026-08-14

## D-001 — 최신 기획과 기존 API 계약의 경계

- **무엇을:** 이번 결과물을 기존 API·DB를 변경하지 않는 고객용 정적 베타 UI로 한정한다.
- **왜:** 최신 기획에는 회원가입, 실물 검수 조건 재승인, 수거 일정, NFC 등 계약 1.1.0에 없는 필드·상태·API가 있다. 계약 변경은 별도 이슈와 양쪽 승인이 필요하다.
- **검토한 대안:** 계약을 함께 확장(승인 부재로 제외), 최신 기획 화면을 삭제(SSOT 위반), UI 진입점만 구현(채택).

## D-002 — 업로드 제한

- **무엇을:** UI 검증은 기존 계약의 1~4개, JPEG/PNG/WebP, 이미지당 6MB를 사용한다. 정면·측면·내부·시리얼 4개 슬롯으로 안내한다.
- **왜:** 최신 와이어프레임은 최소 3장 JPG/PNG 10MB지만 API 계약과 정면 충돌한다. 실제 연동 가능성을 보존해야 한다.
- **검토한 대안:** 와이어프레임의 10MB 적용(API 불일치), 제한을 표시하지 않음(사용자 오류), 기존 계약 적용(채택).

## D-003 — 정품 표현

- **무엇을:** Figma의 `정품 여부 확인됨` 문구를 `정품 신호: 별도 판정 없음` 또는 `수동 검토 필요`로 바꾼다.
- **왜:** 승인된 계약에서 `authenticitySignal`은 `NOT_EVALUATED | REVIEW_REQUIRED`이며 정품·가품 확정 판정이 아니다.
- **검토한 대안:** Figma 문구 유지(법적·계약 위험), 정품 섹션 삭제(핵심 안전 고지 약화), 계약 언어 적용(채택).

## D-004 — 카탈로그와 시각 데모 후보

- **무엇을:** 데이터 기준은 파우치·카드 지갑·키링 3종을 유지한다. Figma의 여권 지갑은 상세 화면의 시각 데모 후보로 표시하되 API 카탈로그라고 주장하지 않는다.
- **왜:** 최신 기획은 여권 지갑·카드 지갑·네임택·키링 4종, 기존 계약은 파우치·카드 지갑·키링 3종이다.
- **검토한 대안:** 계약 카탈로그 수정(승인 부재), Figma 화면 삭제(디자인 손실), 프레젠테이션과 데이터 계약 분리(채택).

## D-005 — 화면 누락과 상태 변형

- **무엇을:** 접수 불가, 보완 요청, 조건 변경, 주문·보증서 없음은 공용 상태 컴포넌트와 기존 화면의 변형으로 보완한다.
- **왜:** 유저플로우에는 필요하지만 와이어프레임/Figma에 일부 대상 화면이 없다.
- **검토한 대안:** 누락 유지(흐름 단절), 모든 상태를 독립 라우트로 생성(과설계), 상태 변형으로 통합(채택).

## D-006 — ESG 보증서와 MCM Passport

- **무엇을:** 하나의 `Certificate` 상세 화면에 ESG 정보와 Passport 요약을 함께 표시하고 QR/NFC는 진입점으로만 표현한다.
- **왜:** 최신 기획은 NFC Passport, 와이어프레임은 QR 보증서, 기존 계약은 공개 검증 URL을 사용한다.
- **검토한 대안:** 두 별도 제품 모델(계약 없음), QR만 구현(최신 기획 누락), 단일 상세+복수 진입점(채택).

## D-007 — 반응형 전략

- **무엇을:** 402px Figma 시안을 모바일 기준으로 사용하고, 데스크톱에서는 최대폭 앱 셸과 보조 패널/여백으로 확장한다.
- **왜:** 최신 PRD는 웹과 iOS를 언급하지만 제공 디자인은 모바일 고정폭이다. 이번 구현 대상은 Next.js 웹이다.
- **검토한 대안:** 모바일 고정폭만 구현(데스크톱 취약), 임의 데스크톱 전면 재설계(디자인 근거 부족), 모바일 우선 점진 확장(채택).

## D-008 — 디자인 토큰 근접값 통합

- **무엇을:** Figma와 와이어프레임의 근접 중복 회색·간격·글자 크기를 P5의 단일 토큰 스케일로 통합한다.
- **왜:** `#333333/#343434`, 15/16px 같은 차이는 의미보다 제작 흔적으로 판단되며 개별 하드코딩은 유지보수를 해친다.
- **검토한 대안:** 모든 실측값 보존(토큰 파편화), 임의 새 팔레트(브랜드 왜곡), 의미 기반 토큰 통합(채택).

## D-009 — AI·카메라·3D·결제 동작

- **무엇을:** 라우트와 UI 진입점만 만들고 실제 동작에는 `TODO(post-beta):`를 남긴다.
- **왜:** 개발 지시서 G2가 복잡 기능의 실제 구현을 명시적으로 제외한다.
- **검토한 대안:** 브라우저 API/가짜 비동기 구현(범위 확대), 진입점 삭제(흐름 단절), 정적 데모+확장 지점(채택).

## D-010 — Figma와 와이어프레임의 역할

- **무엇을:** Figma 디자인이 완성된 화면은 시각 기준으로, 미완성·누락 화면은 와이어프레임 구조와 Figma 스타일 조합으로 구현한다.
- **왜:** 동일한 화면 이름이라도 Figma의 카피·구조가 최신 와이어프레임과 다르며, 개발 지시서가 최신 기획을 상위 SSOT로 지정한다.
- **검토한 대안:** Figma 1:1 복제(기획 누락), 와이어프레임만 사용(브랜드 디자인 손실), 우선순위에 따른 혼합(채택).

## D-011 — Mock 결제 직후와 완료 데모 신청의 분리

- **무엇을:** Mock 결제 완료 화면은 계약 상태 `PENDING_APPROVAL`로 표시하고, 제작 타임라인과 Passport를 확인하는 `/orders/demo`는 별도의 `COMPLETED` 프레젠테이션 신청으로 구분한다.
- **왜:** 같은 신청이 결제 직후 승인 대기에서 즉시 제작·완료로 점프하면 `ApplicationStatus` 전이와 완료 건에만 발급되는 보증서 규칙을 위반한다.
- **검토한 대안:** 즉시 완료로 표현(계약 위반), Passport 진입 제거(핵심 데모 손실), 두 데모 시나리오의 식별자와 설명을 분리(채택).

## D-012 — 프레젠테이션 전용 식별자

- **무엇을:** Figma 여권 지갑 데모의 신청·보증서·검증 식별자는 `mock-data.json`의 기존 키링 보증서와 충돌하지 않는 별도 값으로 둔다.
- **왜:** 기존 Fixture 식별자를 다른 제품·금액·재사용률에 재사용하면 공개 검증 연동 시 같은 ID가 서로 다른 기록을 가리킨다.
- **검토한 대안:** 기존 키링 Fixture 전체를 화면에 사용(Figma 상세 손실), Mock 계약 변경(범위 밖), 계약 형식을 지키는 프레젠테이션 전용 식별자 사용(채택).

## 현재 보류: 실제 외부 연동이 필요한 항목

- 회원가입·프로필 저장 API와 중복 이메일 오류 계약
- 실제 장인 계정·검수 입력 도구·생산 배정 운영 콘솔
- 실제 결제 취소·환불과 택배사 연동
- 실제 정품 인증 기관과 탄소 검증 기관 연동
- 여권 지갑 외 후보의 실생산 카탈로그 확정
- NFC Passport 식별자와 검증 API
- 결제수단 확장과 실제 결제 제공자 계약

수거 정보, 주문 후 실물 검수 상태, 변경 조건 승인·거절과 여권 지갑 골든 시나리오는 더 이상 보류가 아니다. 현재 MVP의 Mock/Fixture 흐름으로 구현·검증한다. 위 보류 항목만 실제 외부 시스템 연결 시 별도 계약 이슈로 확장한다.
